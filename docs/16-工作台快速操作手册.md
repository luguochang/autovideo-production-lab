# AutoVideo 工作台快速操作手册

这份手册面向第一次使用工作台的人。工作台负责管理项目、生成阶段、人工修改和审批；HyperFrames Studio 负责最后的时间线预览。两者不是同一个页面。

## 1. 打开工作台

先在仓库根目录启动服务：

```powershell
npm.cmd run console:build
$env:AUTOVIDEO_CONSOLE_PORT='3339'
npm.cmd run console:start --prefix workflow-console
```

然后打开：

```text
http://127.0.0.1:3339/
```

不要双击 `workflow-console/index.html`，它需要本地 API 和任务队列。

## 2. 页面怎么读

- 左侧“项目”：切换项目、修改平台/时长/发布范围，或新建工作台项目。
- 中间流程图：每个节点是一个生产阶段，按从左到右、从上到下的依赖关系执行。
- 流程较长时，先点画布右下角的“Fit View / 适配视图”，再选择远端节点；被选节点会持续高亮，人工审查节点会直接打开对应审查页，重复点击不会跳回“配置”。
- 右侧“配置”：选择自动生成或 companion，填写本项目提示词和备注。
- 右侧“产物”：查看或编辑允许人工修改的 Markdown、JSON 或文本。
- 右侧“画面微调”：修改已生成视频中的场景、cue 或画面对象。
- “任务队列”：查看排队、运行、取消请求、失败和完成任务；失败任务可以重试，刷新页面不会丢失。
- “发布中心”：查看 MP4、封面、字幕、QA、标准包和发布元数据缺口；只有绑定视频哈希的发布回执才表示真正发布。
- 底部“最近活动”：查看生成、批准、失败、退回和下游失效记录。

状态含义：

| 状态 | 含义 | 操作 |
|---|---|---|
| 未开始 | 尚未生成 | 点击“生成草案” |
| 生成中 | 任务正在队列中 | 等待，不要重复点击 |
| 待审 | 产物已经生成，等待检查 | 查看产物后批准或退回 |
| 已批准 | 当前版本可供下游使用 | 继续下一个阶段 |
| 需重算 | 上游发生变化，旧产物不能继续使用 | 点击“重新生成” |
| 失败 | 任务失败，保留了错误回执 | 修复原因后重新生成 |

## 3. 创建项目和冻结输入

在工作台点击“新建项目”，选择一种输入方式：

- 粘贴文字稿
- 单个素材文件
- 素材目录
- 口播音频
- 网页与本地快照

本地路径必须位于 AutoVideo 工作区内。网页入口不会在线抓取网址，需先保存 HTML、PDF
或图片快照，再同时登记原网址和本地快照。创建后输入会冻结到
`content/workbench-intakes/<project-id>/input/content-intake/submissions/<sha>/`，路线和路径不可
直接改写；相同输入重复提交会复用原 receipt。

CLI 仍可用于已批准文字稿：

批准文字稿后，在仓库根目录执行：

```powershell
npm.cmd run video:new -- --id <project-id> --narration <approved.txt> --ratio 16:9 --duration <estimate>s --platform Douyin
npm.cmd run video:apply-template -- --project <project-id> --style modern-ip-host-explainer --palette light-apricot
npm.cmd run video:prepare-inputs -- --project <project-id>
```

随后打开工作台，选择对应项目，按流程节点生成。当前默认声音是 CosyVoice 预设 14：中文女、FP32、`speed 1.03`、`seed 7`。

也可以直接执行内部标准路线：

```powershell
npm.cmd run video:run-standard -- --project <project-id> --base-url http://127.0.0.1:3339 --fallback-reference demotext-standard-delivery-v5
```

这条路线仍然保留任务、风格、人工听审、Studio 审片和权利门禁，不会把它们静默标成用户批准。任何普通人工门生成待审产物后，命令都会以 `waiting-for-human` 正常结束；在工作台完成对应人工审核后，再执行同一命令继续。它不会自动启动 Studio、播放音频或合成人工结论。

每次运行都会写入项目根目录 `STANDARD_RUN_RECEIPT.json`，历史回执保存在 `receipts/standard-runs/<runId>.json`。回执绑定当前阶段状态、产物 SHA 和完整项目状态 SHA；失败后重新运行会创建新 run，并用 `resumesRunId` 指向上次运行，而不是把中断运行改写成成功。`paused` 任务停在 `waiting-for-operator`，`queued / running / cancel-requested` 任务只等待现有任务，`failed / canceled` 任务才进入新的 attempt。

如果口播只包含 `AI/API` 等明确逐字母缩写，且专用发音合同已经形成机器批准回执，发音门可以继续；出现 `demo/Codex/GPT-4o/camelCase` 等主观读法时，命令会停在“中英混读上下文探针”。完成专用发音审核后再执行同一命令即可继续。

### 材料路线的六阶段文稿链

选择“资料包”路线时，内容区按以下顺序执行：

```text
事实与观点台账（人工批准）
-> Outline Planner
-> Narration Writer
-> Spoken rewrite / Oralizer
-> Duration Fitter
-> Claim/source review
-> 口播稿人工微调与 Content approval
```

Outline、Writer 和 Oralizer 必须绑定上一 artifact 的 SHA 与当前 prompt SHA；不能跳过中间文件直接粘贴一个看似正确的终稿。Duration Fitter 只检查目标秒数和文本密度，不会改字；显示 `needs-revision` 时回到 Writer/Oralizer 返工。最终 verifier 位于 Duration 之后，重新检查来源、观点类型、逐字摘录、数字和技术英文 token。批准后，工作台会把 sources、suitability、evidence、outline、draft、spoken rewrite、duration 和 verifier 八件套一起冻结。Promptfoo 离线通过不能代替 Evidence 批准或最终人工审稿。

### 接入已有正式项目

已有 `hyperframes-workflow-kit/projects/<project-id>/` 项目时，不必重建输入。打开工作台顶部的“接入正式项目”，填入相对路径，例如：

```text
hyperframes-workflow-kit/projects/batch-smoke-30s-20260720
```

先点击“读取并校验”。它会校验项目目录边界、`NarrationLock`、模板锁、口播文本、生产
manifest、音频交接和规划 bundle 的哈希。确认摘要后点击“接入工作台”。

接入只导入可验证机器证据：`source-register` 会显示为已验证；正式项目中的人工文案、
风格、听审、Studio 审片和公开权利都不会自动继承。已有分镜、编译产物和 QA 会以
“需重算/待协调”保留，不能据此直接渲染或发布。这样可以防止旧文件被误当成新的人工批准。

#### 刷新已接入项目的正式证据

正式项目在工作台接入后，如果 CLI、其他智能体或 HyperFrames 流程又生成了新的 QA、规划或交付回执，点击左侧正式项目路径旁的“刷新正式项目证据”图标。确认框会先说明影响范围，再按 SHA-256 重新读取正式目录。

- 相同哈希：阶段状态、revision、人工批准、项目设置、自定义步骤和本地 override 保持不变。
- 新增或变化：只接入为 `stale/evidence-only`，清除不匹配的批准并让依赖下游变成“需重算”；不会自动变成待审或已批准。
- 本地人工产物与正式证据冲突：保留本地产物，记录冲突，不用正式文件覆盖。
- 正式证据缺失、JSON 非法、项目 ID 不符或字幕/视觉 QA 的输入哈希过期：刷新失败或保留最后证据，不做部分自动批准。

刷新完成后消息栏会分别显示新增、变化、移除和保留本地冲突的数量，并定位最早受影响步骤；持久回执写入 `workflow-console/data/projects/<project-id>/formal-project-refresh.json`。每次批准还绑定当时的 artifact SHA，正式路径原地换文件后旧批准不会继续生效。

### 候选动效审片与项目授权

在“风格探针 -> 探针审片”中，每个 recipe 必须独立完成以下动作：

页面顶部的“动效库生命周期”固定列出全部 8 个 recipe，并分别显示技术探针、真人审片、项目批准数、是否可进生产和下一动作。没有探针的 recipe 也会显示；如果配方定义、生命周期台账或官方来源绑定不一致，页面显示“合同阻断”，所有配方的生产资格都会失败关闭。右侧箭头只切换到该配方现有探针，不代表批准。

1. 播放完整 3-8 秒探针，并查看联系表和时间轴 seek 状态。
2. 勾选九项视觉检查后保存“人工通过”。保存只是审片记录，不会改变全局动效状态。
3. 点击“验收为可用动效探针”，才会把该 recipe 从 `candidate` 显式升为 `probe-passed`。
4. 返回当前正式项目，点击“批准用于当前正式项目”。该批准只对当前项目有效。

三个动作分别绑定探针文件、配方定义和项目 ID。`Candidate A` 只表示基础视觉壳已选定，
不会替代任一动效 recipe 的审片或授权。完整晋级和退役规则见
[`docs/18-动效配方晋级与退役SOP.md`](18-动效配方晋级与退役SOP.md)。

需要离线查看或刷新相同状态时运行：

```powershell
npm.cmd run motion:lifecycle -- readiness --out style-library/motion-library/knowledge-explainer.readiness.json --templates-dir style-library/motion-library/review-templates --json
```

`review-templates/*.human-review.template.json` 只是审片工作表，固定 `authorizesLifecycleTransition=false`，不能手工改成批准回执。

## 4. 修改和重新生成

### 修改分镜或文字摘要

1. 点击“语义节拍与分镜”节点。
2. 打开“产物”，编辑允许修改的 JSON/Markdown。
3. 填写修改原因并保存。
4. 点击“重新生成”。
5. 观察下游节点变为“需重算”，按依赖顺序重新生成。

### 修改画面而不重做配音

1. 点击“HyperFrames 全片制作”或“Studio 最终预览”。
2. 打开“画面微调”。
3. 选择场景、cue 或画面对象的稳定 ID。
4. 只填写需要改变的字段，例如屏幕摘要、人物姿态或左右布局。
5. 填写修改原因，点击“保存画面微调”。
6. 重新生成“HyperFrames 全片制作”，再依次完成 QA、Studio 预览、渲染、交付 QA 和标准包。

保存画面微调不会重做配音和 alignment，但会让全片制作及所有交付下游变为“需重算”。撤销会保留历史，不删除审计记录。

### 使用语义动效建议

1. 打开“HyperFrames 全片制作 -> 画面微调”，目标层级选择“节拍”。
2. “语义动效建议”会显示推荐 recipe、最多三个备选、命中的口播语义、缺失输入和生产门禁。
3. 如果推荐与当前配方相同，按钮显示“当前配方”；如果 recipe 仍是 `candidate/probe-passed` 或缺少 Graph IR、claim、界面/代码/证据素材，按钮保持禁用，并直接说明原因。
4. 只有输入完整且 recipe 已获当前项目许可时，“使用建议”才会预填配方和修改原因。仍须点击“保存画面微调”，并重新跑探针、全片、QA 和 Studio 审片。

推荐器不会改动 Q 版人物、`#F2DFC7` 背景、`host.left`、字幕轨或时间轴。历史复盘只参与有界排序，不能自动晋级 recipe，也不能为了多样性改选语义不匹配的配方。

### 为节拍补充视觉素材或 SFX

在同一个“画面微调”面板先选择 cue，再分别使用：

- “从本地视觉素材库导入”：导入已登记的图标、图片、品牌或界面素材；导入后会自动选中当前节拍。
- `npm.cmd run video:sfx-plan -- --project <project-id> --write`：按语义角色和动效配方自动匹配中央 SFX，只导入当前计划实际需要的文件；计划仍是 `candidate/defaultSilent`。
- “从本地素材库导入”：用于人工替换或补充 SFX，只完成冻结和登记，不代表保留或批准。

两类导入都复制文件到项目 `.media`，写入 SHA、来源和许可证回执；不会自动铺满场景，不会自动替换 Q 版人物、`#F2DFC7` 背景或字幕轨。图标只用于强调一个概念，流程关系、数据结论、产品操作和代码证据仍应优先使用真实 Graph IR、图表、截图或日志。

选择 cue 后，工作台还会显示“语义候选”：它依据当前 `shot-manifest`、`visualType` 和素材库别名，最多给出少量去重建议。候选只绑定分镜和素材库哈希，不会自动入画。点击“采用候选”会把素材复制到项目 `.media` 并预填当前 cue 的素材选择；仍须填写画面微调原因并点击“保存画面微调”，素材才会进入下一次全片编译。

资料目录中已经登记的 PNG/JPG/WebP 会在正式项目创建时自动进入 `.media/images/intake/` 候选区，但不会自动挂镜头。它们保留 submission SHA 和 `rightsStatus=needs-review`，必须先确认用途与发布权利，再在 cue 上人工选择。

“素材与发布权利清单”生成 `publication-rights/v2`。内部审片可保留 `needs-review`，但资产 SHA 仍必须匹配；公开清权时，每个 `cleared` 项都要在 `evidence` 中登记一份项目/工作区相对路径、SHA 和凭据类型。网页链接或备注不能代替冻结凭据。旧 v1 清单即使把所有状态改成 `cleared`，也不会获得公开发布资格，必须重新生成 v2。

注意：图标只用于辅助识别，不是主画面证据。流程图仍由 Graph IR 生成；界面、代码、数据证明、证据图和物件隐喻必须使用对应的真实主载体。工作台允许预填图标，但 compiler 不会让图标冒充这些主载体通过 QA。

SFX 统一在画面微调顶部“稀疏语义音效”逐项试听并选择“保留”或“静音”。只保存进度不会入轨；全部候选有决定后才能点击“批准选中音效”。批准回执绑定候选计划 SHA，缺失或篡改时 compiler 会拒绝，不得手工把 JSON 状态改成 `approved` 绕过听审。

每个候选可以明确选择“采用候选”或“不采用”：

- 不采用时必须填写可执行原因，例如“真实流程图已经表达此概念”或“连续两个 cue 已使用相同图标”；只写“不要”不能保存。
- 已保存的决定仍可修改。再次提交会产生 `r2`、`r3` 等新 revision，并通过 `supersedes` 指向上一版，不覆盖审计历史。
- 项目当前决定保存在正式项目的 `review/visual-asset-feedback.json`；跨项目只追加日志保存在 `style-library/assets/feedback-log.jsonl`。
- 候选回执绑定当前 `shot-manifest`、素材库 registry 和候选 digest。分镜或素材库变化后，旧回执不会被当成当前决定，必须刷新后重新判断。
- 工作台显示的全局采用率和素材维度统计只计算每个候选的最新 revision；批次面板也按当前正式 feedback receipt 或最新 revision 去重，采用后改为驳回不会双计。批次中的 recipe/media/text 覆盖数读取当前有效 overrides，不统计已撤销历史。这些指标用于发现素材缺口，不会自动晋升素材、自动入画或替代人工审片。

## 5. 审听和最终审片

- “中英混读上下文探针”：打开右侧“发音审核”，先核对术语类型、IPA/CMU 和原句上下文。候选都是已经导入项目的本地 WAV，不会自动播放，也没有麦克风或录音入口。逐个手动播放到结尾，选择一个候选，再将结论设为“接受已选读法”；需要重做时必须写清问题。全部候选完成后先保存，再点击“冻结本项目发音表”。普通“批准”不能绕过该页。
- “配音候选 A/B 与正式晋升”：点击生成只会新增 `candidate-NNN`，不会覆盖已有正式 WAV。页面会同时列出只读 baseline 和最多两个新候选；逐个手动播放到结尾，选择一个可晋升的新候选，勾选自然度、呼吸、发音、接缝和无杂音五项，选择“接受”并保存 A/B 审核，最后点击“晋升为唯一正式 WAV”。baseline 只能比较，技术 QA 或普通“批准”都不能代替这一步。
- 候选晋升成功后，工作台才原子更新正式 WAV、recipe、听审、批准和音频交接，并把 alignment、字幕、分镜、HyperFrames 时序及渲染标为需重算。若中途失败，系统恢复旧正式文件；不要手工复制候选去覆盖 `audio/narration.final.wav`。
- 发音审核和配音候选都只读取导入项目的本地 WAV，`preload=none` 且不会自动播放。自动化测试不得调用麦克风、录音或外放；当前页面也没有麦克风入口。只有用户后续明确授权，才允许另行测试麦克风。
- “Studio 最终预览”：先由工作台启动 Studio，再播放完整时间线；确认画面、字幕、人物动作和口播同步后，回到工作台提交用户全片审片批准。
- 只有人工听审、全片审片和公开权利都通过，才允许生成 `master.mp4`。否则只生成带 `internal-review` 名称的内部文件。

五项终审未全部勾选时，`final-preview` 保持“待审”。工作台只接受专用五项终审接口；
普通“标记批准”不能批准这一节点。Studio 已启动、`qa-review` 已通过且五项全部确认后，
工作台会一次性写入与当前 composition 绑定的 `human-review` 回执。

## 6. 任务队列与发布中心

- 正在运行的任务选择“取消”后会进入 `cancel-requested`；底层进程完成时不再晋级产物，不是强杀外部进程。
- 失败任务使用“重试”；服务重启后，原 `queued/running` 任务会重新排队。
- 发布中心的“内部审片包”“公开母版候选”“已发布”是不同阶段。MP4 存在不等于已经发布。
- 标题、简介、标签或发布回执缺失时，发布中心会列为缺口；当前仍需在正式产物/回执中补齐，不要手工把阶段改成完成。

### 批次门禁汇总

“批次管理”会在每个批次下显示项目级门禁摘要：

- 默认目标步骤“自动运行到下一人工门”会逐项目执行当前第一个未完成机器步骤；该步骤完成后继续下一步，遇到 `needs-review` 时批次显示“等待人工确认”。
- 完成人工确认后点击同一批次的运行按钮即可继续，不需要新建批次；它不会自动点击批准，也不会跨过发音、配音、字幕、分镜、屏幕文字、Studio 或权利门。
- 每个任务记录输入快照 SHA、幂等键、attempt 和实际落盘产物 SHA；冻结入口还会把 content-intake payload SHA、字节数和文件数写进快照。相同冻结输入与未变化产物才会复用；旧式未冻结 `sourcePath` 不复用已完成的素材登记，失败只重试到批次 `retryLimit`。
- 两次并发点击同一阶段只会预留一个逻辑任务；另一次显示 `reuse`，不会重复生成。批次详情保留 `runHistory` 和逐项目 `queue / reuse / wait-human / complete / blocked` 计划；运行中回执没有结束时间，进入完成、失败、取消或等待人工后才写结束时间。

- `可进全片编排`：风格探针、权利范围、音频交接和 composition readiness 均已批准；仍需 HyperFrames 全片 QA 和人工审片。
- `可交付`：最终预览到标准包的步骤均已批准；公开发布仍单独受发布权利和平台回执约束。
- `有前置阻塞`：显示下一道阻塞步骤和建议动作，例如“素材登记 / 生成该步骤”“配音人工听审 / 完成人工审核”或“需重算 / 重新生成该步骤”。

点击项目摘要会切换到该项目，不会自动批准或改变发布范围。批次会按受限 `retryLimit` 自动重试机器失败；任一步骤修改后应刷新批次再执行。

### 字幕与画面文字三道门

文字质量现在分成三个独立步骤，不能互相替代：

1. “字幕与画面文字 QA”是机器检查，读取当前 `alignment.cues` 与 `captions/narration.zh-CN.srt`，检查逐字文本、时间轴、cue 数量、CPS、重复和空字幕，并写入 `qa/subtitle-qa.json`。
2. “字幕语义人工审校”逐 cue 检查语义、术语、断句、标点和时间可读性。
3. “成片屏幕文字与 OCR 复核”在 HyperFrames check 之后逐张检查当前 composition 的关键抽帧，确认字幕安全区、遮挡、文字准确性、对比度、换行溢出和整段口播重复。

机器状态为 `passed` 只会开放下一道人工门。回执中的 `humanSemanticReview=needs-review` 和 `ocrReview=unavailable` 不是失败，也不是人工通过。

#### 字幕语义人工审校怎么操作

1. 生成“字幕语义人工审校”，打开右侧“字幕审校”。
2. 逐条阅读 cue 的时间、原文和上下文，为每条选择“通过”或“退回修改”。选择“退回修改”时必须写清原因。
3. 完成语义、术语、断句、标点、时间可读性五项清单，点击“保存审校进度”。工作台不提供“一键全部通过”。
4. 所有 cue 都通过后，点击“批准字幕语义审校”。回执绑定当前 `NarrationLock`、alignment、alignment validation、SRT 和 subtitle QA 的 SHA-256。
5. 有退回项时，回到 `content-approval`/`narration-lock` 或 `audio-align` 处理，再按依赖重新生成。不要直接改 SRT 或人工批准文件。

任一绑定文件变化后，旧批准自动失效。普通节点的“批准”接口也不能绕过逐条审校。

#### 成片屏幕文字与 OCR 复核怎么操作

1. `full-production` 会按每个 cue 的中点生成确定性快照；`qa-review` 通过后生成“成片屏幕文字与 OCR 复核”。
   本步骤会尝试运行本地 RapidOCR。需要单独重跑时使用 `npm.cmd run video:ocr -- --project <project-id>`。
2. 打开右侧“文字复核”，逐张查看 16:9 预览、时间点、cue/scene、路径和短哈希，为每张选择“通过”或“退回修改”。联系表和 `finding-*` 诊断裁剪不会冒充独立审片帧。
3. 默认选择“人工逐帧”。这只证明人工复核完成，批准回执明确记录 `reviewMode=manual`。
4. 只有服务端存在与当前 composition、HyperFrames check、frame-set 和逐帧 SHA 全部匹配，且零 unresolved 的 OCR 回执时，才能选择“OCR 报告 + 人工”。页面会分别显示“当前有效 / 未解决 / 引擎不可用 / 报告过期”；后三种状态保持人工模式。OCR 仍不能替代人工判断遮挡、动态终态和重复信息。
5. 七项清单和全部抽帧都通过后才能批准。有退回项时点击“去画面微调处理”，保存 override，重新生成全片、check 和抽帧，再重新复核。

如果该节点显示“尚未到达”，这不是服务器错误。工作台会列出仍缺的字幕人工批准、HyperFrames 成片检查和逐帧复核包；按清单完成上游后再运行本步骤。工作台不会用 `ENOENT` 等内部错误冒充可操作状态，也不会提前生成或批准人工结论。

composition、HyperFrames check、字幕人工批准、frame-set、任一图片字节或 OCR 回执变化后，旧屏幕文字批准都会失效。该步骤只覆盖绑定的关键抽帧；最终仍须在 Studio 从头到尾播放完整时间线。

#### 字幕 QA 的修改、退回和重跑

字幕 QA 是机器报告，不是编辑器。发现错字、断句、时间错位或漏字幕时：

1. 在“字幕与画面文字 QA”节点点击“退回修改”，填写可执行原因，例如“cue-003 术语与 NarrationLock 不一致”。
2. 回到产生问题的上游输入。文字变更必须回到 `content-approval`/`narration-lock`，声音或时间变更必须回到 `voice-final`/`audio-align`；不要直接改 `qa/subtitle-qa.json`、最终 WAV 或锁定 SRT。
3. 保存上游产物后点击“重新生成”。工作台会把字幕 QA 及其下游标记为“需重算”；按依赖顺序重新生成，确认新的 `alignmentSha256`、SRT 哈希和 cue 数量后再继续。
4. 机器通过后，进入专用“字幕语义人工审校”；屏幕文字在 HyperFrames check 后进入专用逐帧复核。两者都不能用普通“确认完成”替代。

#### 视觉丰富度 QA 的修改、退回和重跑

“视觉丰富度 QA”读取当前 `plan/shot-manifest.json`、`storyboard.json` 和 `graph-ir.json`，检查 `visualType`/recipe 分布、连续重复、屏幕摘要是否压缩、图解是否绑定 Graph IR，以及资产型画面是否有冻结来源。它防止整片退化成纯文字 PPT，但不判断画面是否好看、节奏是否舒服或人物是否自然。

1. 先打开报告详情，记录失败项或 warning 对应的 cue ID；不要手工编辑 `qa/visual-variety-qa.json`。
2. 需要改画面时，在“HyperFrames 全片制作 -> 画面微调”选择稳定的 scene/cue/object ID，填写修改原因并保存 override；需要改载体或配方时，在“语义节拍与分镜/视觉计划”的产物中修改 `visualType`、`motionRecipeRefs`、摘要或 Graph IR。
3. 点击“退回修改”后重新生成视觉计划/图解资产，再运行“视觉丰富度 QA”。如果只改了 composition 对象，也必须重新生成“HyperFrames 全片制作”，并重新执行 `hyperframes check`、Studio 预览和交付 QA。
4. 机器报告 `passed` 只表示分布和合同满足阈值；还要播放 3-8 秒动效探针、确认人物仍固定在左侧、背景仍为 `#F2DFC7`、镜头只作用于 `content-world`，最后做 Studio 全时间线审片。

正式样例 `batch-smoke-30s-20260720` 的视觉丰富度机器检查为通过：6 个 cue 使用了 `keyword=3`、`diagram=2`、`comparison=1`，最大连续相同载体/配方为 1。当前仍没有 cue 绑定已批准的辅助素材或 SFX；自动 SFX 计划已经提出 2 个本地候选，但都保持静音并等待真人决定。这不是机器失败，却要求在全片前逐项决定“补素材/保留或静音 SFX”，不能因为报告通过就跳过人工审美。

#### 结构化主载体怎么改

1. 打开“HyperFrames 全片制作 -> 画面微调”，目标层级选择“节拍”或“画面对象”。
2. 在“结构化主载体”中选择图表、代码或界面状态。工作台会同步选择匹配的高级动效配方；配方未获得当前项目准入时选项不可用。
3. 填写标题、载体专属字段、证据标签和本地证据回执。不要填写 URL；示意数据/示意界面只能用于技术探针，不能在这里伪装成真实证据。
4. 保存后查看失效范围。只改数据重编全片；换 adapter 需要重看 style probe；换证据要重新经过 rights-clearance。
5. 重新生成全片并执行 strict check，再进入屏幕文字复核和 Studio 全片审片。撤销时使用覆盖历史右侧的撤销图标。

结构化主载体和 primary image 互斥。选择载体会清除主图但保留辅助 icon；选择主图会清除载体。画面微调页现在按字段显示“自动生成 / 人工覆盖 / 当前有效”三值，并在覆盖历史上方单独显示“当前成片已包含 / 等待重新生成全片”。“当前有效”只是下一次编译输入；看到“等待重新生成全片”时，必须重新执行全片制作，不能把它理解成已写入旧 MP4。保存或撤销若提示 revision 已过期，先重新加载编辑器再决定如何提交，不能直接覆盖另一位编辑者的新 revision。

项目内 `review/carrier-adapter-probes/` 是技术组件回归，不会自动出现在正式配方探针审片页，也不会晋级生命周期。它们的 `humanReview` 仍为 `pending`。

## 8. 不要直接改的文件

- 不要直接修改 `NarrationLock.json`、最终 WAV、alignment 或已编译的 `production/hyperframes/*.html`。
- 不要手工把机器 QA 回执改成“已批准”。
- 口播文字或声音改变时，必须重新生成全部时间依赖产物；画面微调才使用 `overrides/overrides.json`。

每次运行都应保留 `RUN_EXECUTION_LOG.md`、`PIPELINE_RUN_LOG.md`、`PROCESS_LOG.md`、`RETROSPECTIVE.md` 和 `SOP_STATUS.json`，它们是后续复用和追踪的依据。
