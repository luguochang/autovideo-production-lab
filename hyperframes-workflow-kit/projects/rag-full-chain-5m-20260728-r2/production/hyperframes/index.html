pseudocode · 归根结底，RAG 是一套工程系统，不是单纯的提示词技巧，
01 SOURCE: cue-237
02>STEP_1: 归根结底
03 STEP_2: RAG 是一套工程系统
04 STEP_3: 不是单纯的提示词技巧
示意内容口播逻辑示意
我按数据流把 RAG 全链路讲一遍。
整个链路分两段：离线建库把文档变成可检索的库，在线检索把查询变成答案，中间智能体式决策是分水岭。
我顺着数据流一步步讲，每一步都说清楚有哪些选型、生产上一般怎么选、为什么这么选，实际是否组合使用、怎么组合，看哪些指标，还有哪些提升空间。
因为 RAG 的每一步都不是非此即彼的单选，实际生产更多是组合使用。
把这些判断讲清楚，才能体现真正做过，而不只是会调 API。
链路第一站是文档解析。
原始文档可能来自 PDF、Word、HTML 或 Confluence，格式复杂，既有表格、图片，也有扫描件。
这一步的目标是把异构文档变成结构化文本加元数据，解析质量会直接影响后面各环节的效果，垃圾进，垃圾出。
先看解析工具，大致有这么几类。
一类是通用解析库，PyMuPDF、pdfplumber，快但只能拿纯文本，丢结构；一类是结构化解析框架，候选包括 Unstructured、MinerU 和 Docling。
它们支持的格式、中文复杂文档效果、公式和表格还原能力，要用同一批样本比较；商业服务如 LlamaParse 也可以列入候选；扫描件和图表可以用多模态 LLM 兜底，但成本通常更高。
具体到解析工具，先看文档复杂度。
简单纯文本可以先用 PyMuPDF，速度快，成本也低；复杂文档——表格多、层级深、有规范编号——通常要用结构化解析，因为后面要按结构分块、要表格检索，丢了结构这些全做不了。
我自己的判断是，中文复杂文档场景 MinerU 优先，通用多格式场景 Unstructured 优先。
落地时，还有一个关键点：生产上很少只用一个解析器，而是采用分层组合。
主解析用 MinerU 或 Unstructured 跑全量，拿到标题树、表格、阅读顺序；然后过一层规则清洗，去页眉页脚、修乱码、补页码缺失；碰到扫描件、复杂图表、公式这种主解析搞不定的，再触发多模态 LLM 二次解析，成本更高，但更适合处理这些难页，只在需要时使用。
表格要单独整块保留，别被切碎。
所以，只说“用 MinerU”并不准确。
更准确的说法是：以 MinerU 为主解析，再配规则清洗和多模态 LLM 兜底。
MinerU 是主引擎，但不是全部。
那解析质量怎么验收？
这一步自动化指标不多，主要还是靠抽检。
建立几十篇文档的评测集，人工标注正确解析结果，重点看三项：表格还原率；字段完整率，也就是关键数字和专名有没有丢失；以及标题层级识别准确率。
把基础解析跑稳以后，还可以从三条线继续提升：用多模态 LLM 处理复杂页面，评估 ColPali 这类直接检索页面图像的思路，跟进 Docling 在公式和表格上的能力；解析后的结构校验，也可以用规则加小模型自动完成，减少人工抽检。
解析完拿到结构化文本，要切成文本块。
为什么切？
两个原因：LLM 上下文有上限，塞太多又贵又中间信息遗失；整篇文档一起向量化，语义会被稀释。
一篇文档既讲主题一又讲主题二，生成的向量可能同时偏离两类主题。
切成小片段，每片语义聚焦，检索精度高。
分块方式主要有五种。
固定长度切，简单但会切断句子；递归字符切分，按段落、行、空格优先级递归切，LangChain 的递归字符切分器是这个，常见兜底选择；语义切分，用向量化算相邻句子相似度，骤降处切，精度潜力较高，但要逐句向量化慢且贵；markdown 标题切分，按标题层级切带祖先路径，LlamaIndex 的 Markdown 节点解析器，更适合标题层级清晰的结构化文档；还有 Jina 2024 年的延迟分块，先整篇用长上下文向量模型整体向量化，再按文本块边界对词元向量做池化，让每个文本块吸收整篇上下文。
分块怎么选，核心看文档结构。
结构化文档——技术文档、知识库、规范——按标题或条款切，天然有语义边界；通用纯文本用递归字符切；对召回质量要求高且文档量不大的场景才上语义切分。
一个常见起点是 512 词元配 10% 重叠比例，但它不是固定答案，仍要用领域评测集校准。
真正落地时，仍然是组合策略。
生产上一般按文档类型分策略，不是全局一个切法。
比如同一个库里，施工规范按条款条文切，工艺手册按步骤切，表格整块保留带表头上下文，普通说明文字用递归切。
而且切完每个文本块都要带上元数据——来源、章节、页码、条文号、版本，这些后面条件过滤、引用展示、索引重建全要用。
还有一个容易忽略的点，LlamaIndex 生产指南强调的检索块和合成块要解耦：检索用小文本块精度高，合成喂 LLM 时取该文本块前后窗口或整篇，上下文完整。
朴素 RAG 往往把两者当成同一个对象，生产上需要把检索块和合成块解耦。
分块效果不能只凭感觉，至少要看三类信号：文本块内聚度，也就是同一文本块内句子向量的平均相似度；边界切断率，抽检有没有切断关键句和表格；最后再用下游召回率验证。
分块还想继续提升，可以沿三个方向走：用延迟分块带入整篇上下文，但前提是向量模型支持长上下文；用下一节的上下文检索补充位置和主题；或者根据内容密度做动态分块。
分块后、向量化前，其实可以插一步上下文增强。
这一步经常被跳过，但我认为它是值得优先评估的增强项，所以单独讲。
问题在哪：一个文本块脱离原文后语义自足性差。
比如，某个文本块只写“它的定价是每月 50 元”。
脱离原文，你根本不知道这里的“它”指谁，生成的向量也会很模糊，检索时就容易捞不到，或者捞错。
这类上下文增强，目前主要有两个方向。
一个是 Anthropic 2024 年 9 月的上下文检索，用 LLM 给每个文本块生成 50 到 100 词元的上下文前缀，说明它在整篇里的位置主题，拼到文本块前再向量化；一个是前面讲的延迟分块，从向量化层面让文本块带整篇上下文。
上下文检索值不值得上？
公开实验结果很有参考价值，但还要结合自己的成本边界。
按 Anthropic 2024 年 9 月发布的材料，检索失败率从 5.7% 降到 1.9%，相对下降 67%。
这些数字只代表其公开实验，不能直接当作项目承诺。
它不需要额外训练模型，但如果不给提示词做缓存，每个文本块都重复携带整篇文档，成本会迅速放大。
该材料还给出了当时的缓存价格示例；真实成本要按当前价格和自己的文档规模重算。
框架通常需要自己组装这条链路。
具体接入链路时，这一步是可选增强，不是所有项目都要上。
我的判断是，如果文本块切得比较小、或者文档语义关联强、或者召回质量不达标，就值得上上下文检索；文档本身语义自足、量又大，可以先不上控成本。
如果想叠加两路收益，向量化和 BM25 都要使用增强后的文本。
可以和延迟分块二选一或组合，看向量模型支不支持长上下文。
这套增强值不值得上，要靠对照实验回答：先比较基础方案和上下文增强方案的检索失败率，再看下游答案正确率和上下文精度。
如果对照实验确认有收益，再继续比较三件事：上下文检索和延迟分块是否组合，用什么模型生成上下文前缀，以及生成前缀的提示词怎么优化。
文本块准备好，接下来向量化。
向量模型把文本变定长向量，向量相似度约等于语义相似度，这是检索精度的地基。
向量模型先分开源和商业两类。
中文开源候选包括 BGE 系列；需要稠密、稀疏和 ColBERT 多种模式时，可以评估 bge-m3。
商业候选包括 OpenAI、Voyage 和 Cohere 的向量模型；Jina 的长上下文模型可以配合延迟分块。
具体版本、维度和输入类型，要以当前文档和同一套领域评测为准。
向量模型怎么选？
主要看三个方面。
第一是中文效果，BGE 系列通常是中文开源方案的重要候选，但仍要用领域评测集比较。
第二是部署边界，企业知识不能出域时优先评估本地模型；允许外部服务时，再把 OpenAI、Voyage 等商业方案放进同一评测。
第三是维度，3072 维的存储和检索成本更高，是否降到 1024 维，也要用召回指标确认。
我的默认起点是中文企业场景先评估 BGE，需要 ColBERT 能力时再评估 bge-m3。
这里有三个很容易踩的坑。
第一，查询和文档要使用相互兼容的向量模型配置；对区分输入类型的模型，要分别标明查询输入和文档输入，搞反会影响精度。
第二，换模型等于全库重新计算向量，要用版本字段做灰度切换。
第三，MTEB 榜单只能作为参考，最终要看自建领域评测集的召回率。
向量模型选得对不对，重点看三件事：MTEB 榜单只作参考，领域评测集前若干结果的召回率才是关键，同时还要看向量化计算吞吐。
后续优化可以从能力、成本和领域适配三条线展开：评估 bge-m3 的多模态能力，用 Matryoshka 降维节省存储；有标注数据时，再考虑领域微调和指令微调。
向量存哪、怎么检索，这是向量库和索引的事。
向量库的候选包括 pgvector、Milvus、Weaviate、Qdrant、Chroma 和 Elasticsearch。
pgvector 的优势是复用 PostgreSQL 的事务和联表能力；Milvus 面向分布式扩展；Weaviate 内置混合检索；已有 Elasticsearch 技术栈时，也可以复用它的全文和向量能力。
常见索引算法包括 HNSW、IVF 和 Flat。
它们分别偏向低延迟、高规模或精确基线，具体选择要看压测，不能只按数据量贴标签。
向量库怎么选，核心看三件事：规模、是否要事务和联表、运维成本。
我的判断是：在中小规模、已有 PostgreSQL、又需要事务和联表的场景里，可以先评估 pgvector。
理由很实在：后端团队熟悉 SQL，可以先按元数据过滤，再按向量相似度排序，还能跟业务表联表、走事务，少运维一个中间件。
规模、延迟或分片需求超过单库能力后，再评估 Milvus 等分布式方案。
需要内置混合检索时，可以把 Weaviate 放进候选。
具体迁移阈值不能只看片段数量，要用压测决定。
以 pgvector 为例，一般同时建 HNSW 向量索引和 PostgreSQL 全文索引，为在线多路检索铺路。
一个库管理两种索引，不用再单独引入 Elasticsearch。
HNSW 参数可以先从常见组合开始压测。
构建阶段调整连接度和构建深度，查询阶段再调搜索深度，通常要在召回和延迟之间取舍。
还要配合元数据打标，检索时先缩小候选集。
pgvector 的索引维护和空间回收也要进入运维计划。
在我参与的一个知识智能体项目里，我们选择 pgvector 的重要原因之一，就是它能和业务数据共享事务边界。
向量库和索引不能只看速度。
ANN 召回率要先和 Flat 暴力搜索对比，再结合 QPS、延迟 P99 和内存占用设定业务门槛；95% 可以作为一个评估起点，但不是所有场景的统一标准。
数据规模继续增长时，再逐步考虑 HNSW 参数调优、用乘积量化或标量量化降低内存，以及多级索引、分片和倒排文件索引配乘积量化这类超大规模组合。
离线建库讲完，进入在线，从查询开始。
查询进来先别急着检索，先做查询理解——判断这个查询怎么处理。
查询理解可以拆成两块。
一块是查询改写：多查询扩展，让 LLM 把一个查询改成多个不同角度；HyDE，先让 LLM 生成假设答案文档再用它检索；后退一步改写，把具体问题抽象成更高层问题；问题分解，把复合问题拆成子问题。
另一块是查询路由：Adaptive RAG，也就是自适应 RAG 的思路，事前判断查询复杂度路由到不检索、单次检索、多跳检索。
查询改写要不要做，关键看是不是所有查询都值得改写。
简单事实查询直接检索就好，改写反而引入噪声、增加延迟和成本。
所以一般先做自适应路由判断，简单的直接走，复杂的才改写或多跳。
改写策略里，多查询扩展适用面相对广；HyDE 对概念性、方法性查询可能有效，但在事实查询里也可能因为假设错误把检索带偏，这个风险要单独评测。
落地时，我通常把路由判断和按需改写组合起来。
先用分类器或大模型路由器判断查询类型，决定走哪条路：简单的不检索或单次检索，复杂的触发改写和多跳。
改写也不是四种方法全上，根据查询特点选——模糊的用多查询扩展，概念性的用 HyDE，复合的用问题分解。
多轮对话场景还要结合会话上下文做指代消解和条件补全，这个用 Redis 管会话。
查询理解有没有带来收益，主要看改写后前若干结果的召回率是否提升、路由准确率的混淆矩阵，以及人工评估的改写质量。
查询理解跑稳以后，可以继续评估自适应 RAG 的事前路由，也可以微调查询改写模型，或者利用历史日志学习改写策略。
查询理解完，正式检索。
这一步是召回的主力。
检索方式可以先分成几类：纯向量检索，懂语义但关键词匹配弱；纯 BM25，精确关键词但不懂语义；混合检索，BM25 加向量两路互补；更激进的多路，向量加全文加编号精确加表格，各管一类。
BM25 的参数可以先用论文里的常见默认值，再用自己的领域数据校准。
检索这一层，先要认清纯向量检索会在两类查询上翻车。
第一类是编号查询，比如“GB 50204 第 4.1.2 条”，向量容易把编号当普通文本，匹配不准。
第二类是术语精确查询，它要求字面命中。
所以生产上通常至少要评估混合检索，补 BM25 关键词路。
如果场景里编号、术语、表格多，再评估多路检索，把编号精确匹配和表格检索也单独建索引。
真正跑在线链路时，我一般至少从混合检索起步。
向量路使用 pgvector，关键词路使用 PostgreSQL 全文检索，两路并行，各取前五十条候选。
规范文档场景会加到四路：向量、全文、用正则做结构化的编号精确匹配，以及把表格内容单独建索引的表格检索。
每一路负责一类查询。
BM25 中文要分词，用 jieba。
具体几路要看场景。
每加一路都可能补充召回，也会增加噪声和延迟，最终要看离线指标和压测。
在我参与的一个规范文档项目里，我们采用过四路混合检索，它是提升召回率的关键因素之一。
召回层是否有效，先看前若干结果的召回率和命中率，再和单路检索做对比，确认多路组合是不是真的带来提升。
召回还不够时，优先从三处优化：增加真正有区分度的专用索引，调整各路候选数量，再用元数据预过滤缩小候选集。
多路检索拿到的是多份候选，各路分数尺度不一样——向量相似度 0 到 1，全文是 BM25 分，编号是 0 或 1，不能直接加，要融合。
融合方案里，RRF 也就是倒数排名融合，只用排名不用分数；加权分数融合，各路加权求和但要先归一化；凸组合。
RRF 是常见默认方案。
融合阶段为什么常从 RRF 开始？
先看它的计算方式：每一路用 1 除以常数加名次，再把各路结果求和；这个常数常取 60。
为什么用排名不用分数？
因为各路尺度不同不可比，直接加权没意义；RRF 只用排名，尺度无关，简单鲁棒，像多评委投票不比绝对分比平均名次。
常数取 60 是常见的论文经验起点，但仍应结合候选规模和离线指标确认。
LangChain 已经提供混合检索加 RRF 的现成组合，可以减少重复实现。
工程上，我通常先用标准 RRF。
但如果某一路明显比其他路准，比如编号精确匹配在格式规则清晰时通常更可靠，可以用加权 RRF 给它更高权重。
一般场景可以先从标准 RRF 开始，再看离线指标是否需要加权。
融合是否真的有增益，可以看融合后的 nDCG、和单路结果的对比，以及双路重叠率。
重叠率太低可能没有互补价值，太高又说明信息冗余。
有了标注数据以后，可以进一步学习融合权重；在此之前，先从加权 RRF 这类可解释方案开始。
融合完拿到前五十条候选，还混着噪声，上重排精排到真正最相关的前若干条。
重排方案主要包括交叉编码器和 ColBERT。
交叉编码器把查询和文档放进同一个 Transformer 做全注意力交互，通常比双塔召回更精细；开源可以看 BGE 系列重排模型，商业服务可以评估 Cohere 和 Voyage。
ColBERT 采用延迟交互，在精度和速度之间折中。
双塔编码器负责稠密召回，本身不等于独立重排。
到了重排这里，先要分清交叉编码器和双塔的区别。
向量召回是双塔，查询和文档各自编码再算相似度，快但粗，适合从大量文本块里粗筛；重排是交叉编码器，查询和文档拼在一起过模型，通常更精细，但计算更慢，更适合精排几十条。
所以架构是先双塔粗召前五十条，再交叉编码器精排前五条或前二十条，不是直接用重排召回。
Anthropic 的公开流程示例采用混合检索取前一百五十条，再重排到前二十条；这是一种参考配置，不是所有模型和任务的统一最优值。
如果采用交叉编码器，可以先评估 BGE 系列的开源重排模型；需要速度和精度折中时，再评估 ColBERT。
候选数量要用离线指标和延迟压测共同决定，前五十条到前一百五十条可以作为起始范围。
LangChain 也可以接入重排模型。
重排值不值得这段额外延迟，关键看重排前后的 nDCG 和 MRR，确认相关项有没有排得更靠前，同时盯住重排延迟 P99。
重排层后续可以继续比较 ColBERT 的延迟交互、ColPali 这类直接处理文档图像的多模态重排，再根据领域数据做模型选型或微调。
检索拿到前若干条证据，到这里是分水岭。
普通 RAG 是直线——检索完直接生成，不管证据够不够都硬答。
智能体式 RAG 是状态机，拿到证据先评估，不够就改写重检，够了才生成，实在不够就拒答。
这一步我多讲点，因为这是智能体式之所以叫智能体式的核心。
这些智能体式方案，可以按反思时机来分。
事前是自适应 RAG，负责检索前路由；事后是 CRAG，也就是纠错型 RAG，检索后用评估器判断检索质量，证据正确就直接用，证据模糊就补网络检索，证据错误就转向网络检索；事中是 Self-RAG，也就是自反思 RAG，用四个反思词元，也就是是否检索、是否相关、是否支持和是否有用，贯穿检索与生成全程，但它需要微调；还有 Reflexion，也就是反思记忆，把每轮失败的反思存进情景记忆，让智能体跨轮学习。
智能体式 RAG 怎么落到生产？
自反思 RAG 原版需要微调，实施门槛较高，多数团队不会直接照搬完整方案。
生产务实做法是用大模型裁判模拟反思——用提示词让 LLM 输出结构化判断，代替微调的反思词元。
思想来自自反思方案，实现则是轻量的。
四个反思时机里，支持性检查，也就是答案是否被上下文支持，是防幻觉的核心，即使不做其他三个，支持性检查也强烈建议做。
落地时，生产智能体式通常先做证据充分性评估、改写重试和拒答组成的轻量闭环，不急着微调。
拿到前若干条证据，先综合证据数、相关度和引用支持率，判断够不够。
不够就改写查询，再检索一次；同时把最大跳数限制在三跳左右，防止死循环。
够了才生成，实在不够就拒答不硬编。
整个决策循环我用 LangGraph 的图状态机实现，不是手搓条件判断和循环，LangGraph 更适合表达带条件分支和循环的决策流。
坑是 LLM 自评有偏差偏好自己答案，关键场景要换更强模型当裁判做交叉评估。
在我参与的一个项目里，我们采用了这套轻量闭环，引用支持率得到明显改善；具体项目名称和数值要在获得公开授权后再披露。
这套闭环不能只看答案漂亮不漂亮，还要看多跳任务成功率、拒答准确率、忠实度和收敛轮数分布；再比较有记忆和无记忆的成功率差值，验证反思记忆到底有没有价值。
轻量闭环跑稳以后，再逐步评估跨轮能力：用反思记忆从失败中学习，按需要尝试自反思 RAG 微调、纠错型 RAG 的网络检索兜底、图谱 RAG 的跨文档推理和全局总结，以及多智能体互评。
证据够了，生成最终答案。
到了生成阶段，先把提示词约束做好：要求只基于资料答、资料没有就说不知道、温度调低 0 到 0.3 减发散。
引用有三种实现。
第一种是在提示词里让 LLM 自己标来源编号，简单，但可能标错。
第二种是后处理校验，生成完成后再用规则或小模型核对引用是否真实。
第三种是片段级引用，让模型直接指出答案片段对应哪个文本块；这种方式通常能给出更细的引用对应，Cohere 提供了相关能力。
到了生成环节，防幻觉是命门，要守住四道防线——支持性检查、温度调低、明确说不知道、引用校验。
LLM 会合理化编造，即使上下文没有也可能编一个看似合理的，支持性检查加引用校验是兜底。
引用我建议提示词级加后处理校验，别光信 LLM 标的号。
具体到生成链路，提示词模板要求每个事实陈述后标来源编号，生成完用后处理校验每个来源编号是不是真存在于上下文且内容对应。
多候选场景可以生成多个答案用有用性检查选最优，但成本翻倍，只对低置信答案做。
答案要返回来源文档、章节、页码、引用片段，这是 RAG 相比纯 LLM 的可信度优势。
生成环节最后看四个结果：引用是不是真实对应，覆盖是否完整，答案是否忠实，以及人工标注的幻觉率。
生成侧还可以继续加强四件事：用结构化输出约束引用格式，逐句做支持性检查，把引用回溯到具体页码和条文号，并给答案标注置信度。
不评测的 RAG 就是瞎调，每改一环都要有指标量化。
评测贯穿全链路。
评测工具里，RAGAS 是常用框架之一。
它主要看四类指标：忠实度，判断答案是否忠于证据；答案相关性，看回答是否切题；上下文精度，看检索结果准不准；上下文召回率，看该找的证据有没有找全。
TruLens 和 DeepEval 也有类似能力；除此之外，还可以用自建黄金问答集配合调用链归因。
检索独立指标有前若干结果的召回率、MRR、nDCG、命中率。
评测怎么落地？
先承认 RAGAS 用大模型裁判也有偏差——偏好长答案、偏好自己风格，要换不同强模型当裁判交叉、多次评判取平均、关键场景加人工校准。
我的判断是，贴合具体场景的黄金问答集加调用链归因比通用 RAGAS 更实用，因为能定位到具体环节。
评测集三种来源混合：LLM 从文档生成查询做量、人工标注做质、生产真实查询采样做校准。
评测闭环可以这样搭：先建 200 条左右黄金问答集，核心指标三个——前五召回率看检索、引用支持率看生成可信、拒答准确率看兜底。
线上每次问答落调用链，记录查询、改写、召回片段、排序分数、引用、提示词版本、用户反馈。
问题样例通过调用链定位到具体环节——是分块切断条文、还是召回没命中、还是生成没挂引用，而不是笼统说效果不好，定位完回流迭代。
在我参与的一个项目里，我们用这套调用链闭环定位并修复问题，前五召回率得到明显提升；具体项目名称和数值要在获得公开授权后再披露。
整条评测链要持续追踪前若干结果的召回率、忠实度、答案相关性、上下文精度和召回率、引用准确率，以及拒答准确率。
评测体系成熟以后，可以进一步全量接入 RAGAS 四类指标，再校准大模型裁判偏差，自动归因问题样例。
下一步，把线上对照实验和持续集成式回归测试接起来，做到每次改动都先验证不退化，再上线。
从演示到生产，还有几件关键工程能力要补齐，这步往往是被忽视但决定能不能上线的。
上线前，通常还要把几组工程能力补齐。
提示词缓存和流式输出，分别控制成本与首字延迟；内容去重和防提示词注入，负责上下文质量与安全；增量索引和版本管理，控制更新成本和模型切换；最后再用监控告警守住可用性。
最后看上线工程，这些能力要组合着选。
在上下文检索这类重复携带长前缀的流程里，提示词缓存应优先评估。
公开材料给出过显著的成本和首词元延迟改善，但真实收益取决于模型、缓存命中率和当前计费规则，不能直接当作项目承诺。
流式输出通常是改善用户体验的重要手段。
防提示词注入是安全重点，检索到的文档里可能藏恶意指令，做法包括：用分隔符隔离文档内容，在系统中明确文档是数据而不是指令，再做输出过滤。
增量索引用内容指纹加版本，文档更新不做全量重建，指纹相同跳过幂等、版本变化只重建差异块。
换向量模型要版本管理，带向量模型版本字段灰度切换。
这些能力不能各做各的，而要组合配套。
提示词缓存配上下文检索；增量索引配版本管理；防注入配输出过滤；全链路监控延迟、成本、错误率和缓存命中率。
pgvector 的 HNSW 删除是标记删除，定期重建索引回收空间，这个运维细节要注意。
到了线上，指标还要扩展到工程侧：可用性 SLA、延迟 P99、单次查询成本、缓存命中率、注入拦截率、增量索引正确性和版本切换稳定性。
SLA 与缓存收益门槛，要按业务目标和成本模型单独设定。
工程侧的下一步，包括多级缓存，也就是查询结果缓存和向量化缓存；还可以做异步增量索引、灰度发布、用混沌测试验证注入攻击防护，并补上成本告警。
第一，RAG 全链路是一条数据流。
离线建库，包括解析、分块、上下文增强和向量化索引，决定系统上限；在线检索，包括查询理解、多路混合、RRF 和重排，决定召回效果；智能体式决策，通过评估、改写重试和拒答，决定回答是否可信；最后，评测闭环决定这套系统能不能持续迭代。
第二，每一步都不是单一选型，生产多是组合——解析是主引擎加规则清洗加多模态兜底，检索是多路混合，智能体式是轻量闭环不微调，关键是要有选型判断和理由，不是调 API。
第三，每一步都有指标，也都有继续提升的空间。
上下文检索要看失败率有没有下降；反思记忆要看智能体能不能从失败中学习；RAGAS 则用四类指标量化质量。
归根结底，RAG 是一套工程系统，不是单纯的提示词技巧，讲究的是每一环都可控、可测、可迭代。
