上一集，我们走完了从原始文档到可检索知识库的离线链路。
这几步决定知识能不能被准确找到。
接下来进入在线部分，看查询理解、召回、重排和智能体决策怎样配
合。
离线建库讲完，进入在线，从查询开始。
查询进来先别急着检索，先做查询理解——判断这个查询怎么处理。
查询理解可以拆成两块。
一块是查询改写：多查询扩展，让 LLM 把一个查询改成多个不
同角度；HyDE，先让 LLM 生成假设答案文档再用它检索；
后退一步改写，把具体问题抽象成更高层问题；
问题分解，把复合问题拆成子问题。
另一块是查询路由：Adaptive RAG，
也就是自适应 RAG 的思路，事前判断查询复杂度路由到不检索
、单次检索、多跳检索。
查询改写要不要做，关键看是不是所有查询都值得改写。
简单事实查询直接检索就好，改写反而引入噪声、
增加延迟和成本。
所以一般先做自适应路由判断，简单的直接走，
复杂的才改写或多跳。
改写策略里，多查询扩展适用面相对广；
HyDE 对概念性、方法性查询可能有效，
但在事实查询里也可能因为假设错误把检索带偏，
这个风险要单独评测。
落地时，我通常把路由判断和按需改写组合起来。
先用分类器或大模型路由器判断查询类型，决定走哪条路：
简单的不检索或单次检索，复杂的触发改写和多跳。
改写也不是四种方法全上，根据查询特点选——模糊的用多查询扩展
，概念性的用 HyDE，复合的用问题分解。
多轮对话场景还要结合会话上下文做指代消解和条件补全，
这个用 Redis 管会话。
查询理解有没有带来收益，主要看改写后前若干结果的召回率是否提
升、路由准确率的混淆矩阵，以及人工评估的改写质量。
查询理解跑稳以后，可以继续评估自适应 RAG 的事前路由，
也可以微调查询改写模型，或者利用历史日志学习改写策略。
查询理解完，正式检索。
这一步是召回的主力。
检索方式可以先分成几类：纯向量检索，懂语义但关键词匹配弱；
纯 BM25，精确关键词但不懂语义；
混合检索，BM25 加向量两路互补；
更激进的多路，向量加全文加编号精确加表格，
各管一类。
BM25 的参数可以先用论文里的常见默认值，
再用自己的领域数据校准。
检索这一层，先要认清纯向量检索会在两类查询上翻车。
第一类是编号查询，比如“GB 50204 第 4.1.2 条
”，向量容易把编号当普通文本，匹配不准。
第二类是术语精确查询，它要求字面命中。
所以生产上通常至少要评估混合检索，补 BM25 关键词路。
如果场景里编号、术语、表格多，再评估多路检索，
把编号精确匹配和表格检索也单独建索引。
真正跑在线链路时，我一般至少从混合检索起步。
向量路使用 pgvector，关键词路使用 PostgreS
QL 全文检索，两路并行，各取前五十条候选。
规范文档场景会加到四路：向量、全文、用正则做结构化的编号精确
匹配，以及把表格内容单独建索引的表格检索。
每一路负责一类查询。
BM25 中文要分词，用 jieba。
具体几路要看场景。
每加一路都可能补充召回，也会增加噪声和延迟，
最终要看离线指标和压测。
在我参与的一个规范文档项目里，我们采用过四路混合检索，
它是提升召回率的关键因素之一。
召回层是否有效，先看前若干结果的召回率和命中率，
再和单路检索做对比，确认多路组合是不是真的带来提升。
召回还不够时，优先从三处优化：增加真正有区分度的专用索引，
调整各路候选数量，再用元数据预过滤缩小候选集。
多路检索拿到的是多份候选，各路分数尺度不一样——向量相似度
0 到 1，全文是 BM25 分，编号是 0 或 1，
不能直接加，要融合。
融合方案里，RRF 也就是倒数排名融合，
只用排名不用分数；加权分数融合，各路加权求和但要先归一化；
凸组合。
RRF 是常见默认方案。
融合阶段为什么常从 RRF 开始？
先看它的计算方式：每一路用 1 除以常数加名次，
再把各路结果求和；这个常数常取 60。
为什么用排名不用分数？
因为各路尺度不同不可比，直接加权没意义；
RRF 只用排名，尺度无关，简单鲁棒，像多评委投票不比绝对分
比平均名次。
常数取 60 是常见的论文经验起点，但仍应结合候选规模和离线
指标确认。
LangChain 已经提供混合检索加 RRF 的现成组合，
可以减少重复实现。
工程上，我通常先用标准 RRF。
但如果某一路明显比其他路准，比如编号精确匹配在格式规则清晰时
通常更可靠，可以用加权 RRF 给它更高权重。
一般场景可以先从标准 RRF 开始，再看离线指标是否需要加权
。
融合是否真的有增益，可以看融合后的 nDCG、
和单路结果的对比，以及双路重叠率。
重叠率太低可能没有互补价值，太高又说明信息冗余。
有了标注数据以后，可以进一步学习融合权重；
在此之前，先从加权 RRF 这类可解释方案开始。
融合完拿到前五十条候选，还混着噪声，上重排精排到真正最相关的
前若干条。
重排方案主要包括交叉编码器和 ColBERT。
交叉编码器把查询和文档放进同一个 Transformer 做
全注意力交互，通常比双塔召回更精细；
开源可以看 BGE 系列重排模型，商业服务可以评估 Cohe
re 和 Voyage。
ColBERT 采用延迟交互，在精度和速度之间折中。
双塔编码器负责稠密召回，本身不等于独立重排。
到了重排这里，先要分清交叉编码器和双塔的区别。
向量召回是双塔，查询和文档各自编码再算相似度，
快但粗，适合从大量文本块里粗筛；
重排是交叉编码器，查询和文档拼在一起过模型，
通常更精细，但计算更慢，更适合精排几十条。
所以架构是先双塔粗召前五十条，再交叉编码器精排前五条或前二十
条，不是直接用重排召回。
Anthropic 的公开流程示例采用混合检索取前一百五十条
，再重排到前二十条；
这是一种参考配置，不是所有模型和任务的统一最优值。
如果采用交叉编码器，可以先评估 BGE 系列的开源重排模型；
需要速度和精度折中时，再评估 ColBERT。
候选数量要用离线指标和延迟压测共同决定，
前五十条到前一百五十条可以作为起始范围。
LangChain 也可以接入重排模型。
重排值不值得这段额外延迟，关键看重排前后的 nDCG 和 M
RR，确认相关项有没有排得更靠前，同时盯住重排延迟 P99。
重排层后续可以继续比较 ColBERT 的延迟交互、
ColPali 这类直接处理文档图像的多模态重排，
再根据领域数据做模型选型或微调。
检索拿到前若干条证据，到这里是分水岭。
普通 RAG 是直线——检索完直接生成，
不管证据够不够都硬答。
智能体式 RAG 是状态机，拿到证据先评估，
不够就改写重检，够了才生成，实在不够就拒答。
这一步我多讲点，因为这是智能体式之所以叫智能体式的核心。
这些智能体式方案，可以按反思时机来分。
事前是自适应 RAG，负责检索前路由；
事后是 CRAG，也就是纠错型 RAG，
检索后用评估器判断检索质量，证据正确就直接用，
证据模糊就补网络检索，证据错误就转向网络检索；
事中是 Self-RAG，也就是自反思 RAG，
用四个反思词元，也就是是否检索、是否相关、
是否支持和是否有用，贯穿检索与生成全程，
但它需要微调；还有 Reflexion，
也就是反思记忆，把每轮失败的反思存进情景记忆，
让智能体跨轮学习。
智能体式 RAG 怎么落到生产？
自反思 RAG 原版需要微调，实施门槛较高，
多数团队不会直接照搬完整方案。
生产务实做法是用大模型裁判模拟反思——用提示词让 LLM 输
出结构化判断，代替微调的反思词元。
思想来自自反思方案，实现则是轻量的。
四个反思时机里，支持性检查，也就是答案是否被上下文支持，
是防幻觉的核心，即使不做其他三个，支持性检查也强烈建议做。
落地时，生产智能体式通常先做证据充分性评估、
改写重试和拒答组成的轻量闭环，不急着微调。
拿到前若干条证据，先综合证据数、相关度和引用支持率，
判断够不够。
不够就改写查询，再检索一次；
同时把最大跳数限制在三跳左右，防止死循环。
够了才生成，实在不够就拒答不硬编。
整个决策循环我用 LangGraph 的图状态机实现，
不是手搓条件判断和循环，LangGraph 更适合表达带条件
分支和循环的决策流。
坑是 LLM 自评有偏差偏好自己答案，关键场景要换更强模型当
裁判做交叉评估。
在我参与的一个项目里，我们采用了这套轻量闭环，
引用支持率得到明显改善；
具体项目名称和数值要在获得公开授权后再披露。
这套闭环不能只看答案漂亮不漂亮，还要看多跳任务成功率、
拒答准确率、忠实度和收敛轮数分布；
再比较有记忆和无记忆的成功率差值，验证反思记忆到底有没有价值
。
轻量闭环跑稳以后，再逐步评估跨轮能力：用反思记忆从失败中学习
，按需要尝试自反思 RAG 微调、纠错型 RAG 的网络检索
兜底、图谱 RAG 的跨文档推理和全局总结，
以及多智能体互评。
证据够了，生成最终答案。
到了生成阶段，先把提示词约束做好：要求只基于资料答、
资料没有就说不知道、温度调低 0 到 0.3 减发散。
引用有三种实现。
第一种是在提示词里让 LLM 自己标来源编号，
简单，但可能标错。
第二种是后处理校验，生成完成后再用规则或小模型核对引用是否真
实。
第三种是片段级引用，让模型直接指出答案片段对应哪个文本块；
这种方式通常能给出更细的引用对应，Cohere 提供了相关能
力。
到了生成环节，防幻觉是命门，要守住四道防线——支持性检查、
温度调低、明确说不知道、引用校验。
LLM 会合理化编造，即使上下文没有也可能编一个看似合理的，
支持性检查加引用校验是兜底。
引用我建议提示词级加后处理校验，别光信 LLM 标的号。
具体到生成链路，提示词模板要求每个事实陈述后标来源编号，
生成完用后处理校验每个来源编号是不是真存在于上下文且内容对应
。
多候选场景可以生成多个答案用有用性检查选最优，
但成本翻倍，只对低置信答案做。
答案要返回来源文档、章节、页码、引用片段，
这是 RAG 相比纯 LLM 的可信度优势。
生成环节最后看四个结果：引用是不是真实对应，
覆盖是否完整，答案是否忠实，以及人工标注的幻觉率。
生成侧还可以继续加强四件事：用结构化输出约束引用格式，
逐句做支持性检查，把引用回溯到具体页码和条文号，
并给答案标注置信度。
不评测的 RAG 就是瞎调，每改一环都要有指标量化。
评测贯穿全链路。
评测工具里，RAGAS 是常用框架之一。
它主要看四类指标：忠实度，判断答案是否忠于证据；
答案相关性，看回答是否切题；
上下文精度，看检索结果准不准；
上下文召回率，看该找的证据有没有找全。
TruLens 和 DeepEval 也有类似能力；
除此之外，还可以用自建黄金问答集配合调用链归因。
检索独立指标有前若干结果的召回率、MRR、
nDCG、命中率。
评测怎么落地？
先承认 RAGAS 用大模型裁判也有偏差——偏好长答案、
偏好自己风格，要换不同强模型当裁判交叉、
多次评判取平均、关键场景加人工校准。
我的判断是，贴合具体场景的黄金问答集加调用链归因比通用 RA
GAS 更实用，因为能定位到具体环节。
评测集三种来源混合：LLM 从文档生成查询做量、
人工标注做质、生产真实查询采样做校准。
评测闭环可以这样搭：先建 200 条左右黄金问答集，
核心指标三个——前五召回率看检索、引用支持率看生成可信、
拒答准确率看兜底。
线上每次问答落调用链，记录查询、改写、召回片段、
排序分数、引用、提示词版本、用户反馈。
问题样例通过调用链定位到具体环节——是分块切断条文、
还是召回没命中、还是生成没挂引用，而不是笼统说效果不好，
定位完回流迭代。
在我参与的一个项目里，我们用这套调用链闭环定位并修复问题，
前五召回率得到明显提升；
具体项目名称和数值要在获得公开授权后再披露。
整条评测链要持续追踪前若干结果的召回率、
忠实度、答案相关性、上下文精度和召回率、
引用准确率，以及拒答准确率。
评测体系成熟以后，可以进一步全量接入 RAGAS 四类指标，
再校准大模型裁判偏差，自动归因问题样例。
下一步，把线上对照实验和持续集成式回归测试接起来，
做到每次改动都先验证不退化，再上线。
从演示到生产，还有几件关键工程能力要补齐，
这步往往是被忽视但决定能不能上线的。
上线前，通常还要把几组工程能力补齐。
提示词缓存和流式输出，分别控制成本与首字延迟；
内容去重和防提示词注入，负责上下文质量与安全；
增量索引和版本管理，控制更新成本和模型切换；
最后再用监控告警守住可用性。
最后看上线工程，这些能力要组合着选。
在上下文检索这类重复携带长前缀的流程里，
提示词缓存应优先评估。
公开材料给出过显著的成本和首词元延迟改善，
但真实收益取决于模型、缓存命中率和当前计费规则，
不能直接当作项目承诺。
流式输出通常是改善用户体验的重要手段。
防提示词注入是安全重点，检索到的文档里可能藏恶意指令，
做法包括：用分隔符隔离文档内容，在系统中明确文档是数据而不是
指令，再做输出过滤。
增量索引用内容指纹加版本，文档更新不做全量重建，
指纹相同跳过幂等、版本变化只重建差异块。
换向量模型要版本管理，带向量模型版本字段灰度切换。
这些能力不能各做各的，而要组合配套。
提示词缓存配上下文检索；
增量索引配版本管理；
防注入配输出过滤；全链路监控延迟、成本、
错误率和缓存命中率。
pgvector 的 HNSW 删除是标记删除，
定期重建索引回收空间，这个运维细节要注意。
到了线上，指标还要扩展到工程侧：可用性 SLA、
延迟 P99、单次查询成本、缓存命中率、
注入拦截率、增量索引正确性和版本切换稳定性。
SLA 与缓存收益门槛，要按业务目标和成本模型单独设定。
工程侧的下一步，包括多级缓存，也就是查询结果缓存和向量化缓存
；还可以做异步增量索引、灰度发布、用混沌测试验证注入攻击防护
，并补上成本告警。
第一，RAG 全链路是一条数据流。
离线建库，包括解析、分块、上下文增强和向量化索引，
决定系统上限；在线检索，包括查询理解、多路混合、
RRF 和重排，决定召回效果；
智能体式决策，通过评估、改写重试和拒答，
决定回答是否可信；最后，评测闭环决定这套系统能不能持续迭代。
第二，每一步都不是单一选型，生产多是组合——解析是主引擎加规
则清洗加多模态兜底，检索是多路混合，智能体式是轻量闭环不微调
，关键是要有选型判断和理由，不是调 API。
第三，每一步都有指标，也都有继续提升的空间。
上下文检索要看失败率有没有下降；
反思记忆要看智能体能不能从失败中学习；
RAGAS 则用四类指标量化质量。
归根结底，RAG 是一套工程系统，不是单纯的提示词技巧，
讲究的是每一环都可控、可测、可迭代。
