离线建库已经完成
下集从查询开始
我按数据流把 RAG 全链路讲一遍。
整个链路分两段：离线建库把文档变成可检索的库，
在线检索把查询变成答案，中间智能体式决策是分水岭。
我顺着数据流一步步讲，每一步都说清楚有哪些选型、
生产上一般怎么选、为什么这么选，实际是否组合使用、
怎么组合，看哪些指标，还有哪些提升空间。
因为 RAG 的每一步都不是非此即彼的单选，
实际生产更多是组合使用。
把这些判断讲清楚，才能体现真正做过，而不只是会调 API。
链路第一站是文档解析。
原始文档可能来自 PDF、Word、HTML 或 Confl
uence，格式复杂，既有表格、图片，也有扫描件。
这一步的目标是把异构文档变成结构化文本加元数据，
解析质量会直接影响后面各环节的效果，垃圾进，
垃圾出。
先看解析工具，大致有这么几类。
一类是通用解析库，PyMuPDF、pdfplumber，
快但只能拿纯文本，丢结构；
一类是结构化解析框架，候选包括 Unstructured、
MinerU 和 Docling。
它们支持的格式、中文复杂文档效果、公式和表格还原能力，
要用同一批样本比较；
商业服务如 LlamaParse 也可以列入候选；
扫描件和图表可以用多模态 LLM 兜底，
但成本通常更高。
具体到解析工具，先看文档复杂度。
简单纯文本可以先用 PyMuPDF，速度快，
成本也低；复杂文档——表格多、层级深、有规范编号——通常要用
结构化解析，因为后面要按结构分块、要表格检索，
丢了结构这些全做不了。
我自己的判断是，中文复杂文档场景 MinerU 优先，
通用多格式场景 Unstructured 优先。
落地时，还有一个关键点：生产上很少只用一个解析器，
而是采用分层组合。
主解析用 MinerU 或 Unstructured 跑全量
，拿到标题树、表格、阅读顺序；
然后过一层规则清洗，去页眉页脚、修乱码、
补页码缺失；碰到扫描件、复杂图表、公式这种主解析搞不定的，
再触发多模态 LLM 二次解析，成本更高，
但更适合处理这些难页，只在需要时使用。
表格要单独整块保留，别被切碎。
所以，只说“用 MinerU”并不准确。
更准确的说法是：以 MinerU 为主解析，
再配规则清洗和多模态 LLM 兜底。
MinerU 是主引擎，但不是全部。
那解析质量怎么验收？
这一步自动化指标不多，主要还是靠抽检。
建立几十篇文档的评测集，人工标注正确解析结果，
重点看三项：表格还原率；
字段完整率，也就是关键数字和专名有没有丢失；
以及标题层级识别准确率。
把基础解析跑稳以后，还可以从三条线继续提升：
用多模态 LLM 处理复杂页面，评估 ColPali 这类直
接检索页面图像的思路，跟进 Docling 在公式和表格上的
能力；解析后的结构校验，也可以用规则加小模型自动完成，
减少人工抽检。
解析完拿到结构化文本，要切成文本块。
为什么切？
两个原因：LLM 上下文有上限，塞太多又贵又中间信息遗失；
整篇文档一起向量化，语义会被稀释。
一篇文档既讲主题一又讲主题二，生成的向量可能同时偏离两类主题
。
切成小片段，每片语义聚焦，检索精度高。
分块方式主要有五种。
固定长度切，简单但会切断句子；
递归字符切分，按段落、行、空格优先级递归切，
LangChain 的递归字符切分器是这个，
常见兜底选择；语义切分，用向量化算相邻句子相似度，
骤降处切，精度潜力较高，但要逐句向量化慢且贵；
markdown 标题切分，按标题层级切带祖先路径，
LlamaIndex 的 Markdown 节点解析器，
更适合标题层级清晰的结构化文档；
还有 Jina 2024 年的延迟分块，
先整篇用长上下文向量模型整体向量化，再按文本块边界对词元向量
做池化，让每个文本块吸收整篇上下文。
分块怎么选，核心看文档结构。
结构化文档——技术文档、知识库、规范——按标题或条款切，
天然有语义边界；通用纯文本用递归字符切；
对召回质量要求高且文档量不大的场景才上语义切分。
一个常见起点是 512 词元配 10% 重叠比例，
但它不是固定答案，仍要用领域评测集校准。
真正落地时，仍然是组合策略。
生产上一般按文档类型分策略，不是全局一个切法。
比如同一个库里，施工规范按条款条文切，工艺手册按步骤切，
表格整块保留带表头上下文，普通说明文字用递归切。
而且切完每个文本块都要带上元数据——来源、
章节、页码、条文号、版本，这些后面条件过滤、
引用展示、索引重建全要用。
还有一个容易忽略的点，LlamaIndex 生产指南强调的检
索块和合成块要解耦：检索用小文本块精度高，
合成喂 LLM 时取该文本块前后窗口或整篇，
上下文完整。
朴素 RAG 往往把两者当成同一个对象，
生产上需要把检索块和合成块解耦。
分块效果不能只凭感觉，至少要看三类信号：
文本块内聚度，也就是同一文本块内句子向量的平均相似度；
边界切断率，抽检有没有切断关键句和表格；
最后再用下游召回率验证。
分块还想继续提升，可以沿三个方向走：用延迟分块带入整篇上下文
，但前提是向量模型支持长上下文；
用下一节的上下文检索补充位置和主题；
或者根据内容密度做动态分块。
分块后、向量化前，其实可以插一步上下文增强。
这一步经常被跳过，但我认为它是值得优先评估的增强项，
所以单独讲。
问题在哪：一个文本块脱离原文后语义自足性差。
比如，某个文本块只写“它的定价是每月 50 元”。
脱离原文，你根本不知道这里的“它”指谁，
生成的向量也会很模糊，检索时就容易捞不到，
或者捞错。
这类上下文增强，目前主要有两个方向。
一个是 Anthropic 2024 年 9 月的上下文检索
，用 LLM 给每个文本块生成 50 到 100 词元的上下
文前缀，说明它在整篇里的位置主题，拼到文本块前再向量化；
一个是前面讲的延迟分块，从向量化层面让文本块带整篇上下文。
上下文检索值不值得上？
公开实验结果很有参考价值，但还要结合自己的成本边界。
按 Anthropic 2024 年 9 月发布的材料，
检索失败率从 5.7% 降到 1.9%，
相对下降 67%。
这些数字只代表其公开实验，不能直接当作项目承诺。
它不需要额外训练模型，但如果不给提示词做缓存，
每个文本块都重复携带整篇文档，成本会迅速放大。
该材料还给出了当时的缓存价格示例；
真实成本要按当前价格和自己的文档规模重算。
框架通常需要自己组装这条链路。
具体接入链路时，这一步是可选增强，不是所有项目都要上。
我的判断是，如果文本块切得比较小、或者文档语义关联强、
或者召回质量不达标，就值得上上下文检索；
文档本身语义自足、量又大，可以先不上控成本。
如果想叠加两路收益，向量化和 BM25 都要使用增强后的文本
。
可以和延迟分块二选一或组合，看向量模型支不支持长上下文。
这套增强值不值得上，要靠对照实验回答：先比较基础方案和上下文
增强方案的检索失败率，再看下游答案正确率和上下文精度。
如果对照实验确认有收益，再继续比较三件事：
上下文检索和延迟分块是否组合，用什么模型生成上下文前缀，
以及生成前缀的提示词怎么优化。
文本块准备好，接下来向量化。
向量模型把文本变定长向量，向量相似度约等于语义相似度，
这是检索精度的地基。
向量模型先分开源和商业两类。
中文开源候选包括 BGE 系列；
需要稠密、稀疏和 ColBERT 多种模式时，
可以评估 bge-m3。
商业候选包括 OpenAI、Voyage 和 Cohere
的向量模型；Jina 的长上下文模型可以配合延迟分块。
具体版本、维度和输入类型，要以当前文档和同一套领域评测为准。
向量模型怎么选？
主要看三个方面。
第一是中文效果，BGE 系列通常是中文开源方案的重要候选，
但仍要用领域评测集比较。
第二是部署边界，企业知识不能出域时优先评估本地模型；
允许外部服务时，再把 OpenAI、Voyage 等商业方案
放进同一评测。
第三是维度，3072 维的存储和检索成本更高，
是否降到 1024 维，也要用召回指标确认。
我的默认起点是中文企业场景先评估 BGE，
需要 ColBERT 能力时再评估 bge-m3。
这里有三个很容易踩的坑。
第一，查询和文档要使用相互兼容的向量模型配置；
对区分输入类型的模型，要分别标明查询输入和文档输入，
搞反会影响精度。
第二，换模型等于全库重新计算向量，要用版本字段做灰度切换。
第三，MTEB 榜单只能作为参考，最终要看自建领域评测集的召
回率。
向量模型选得对不对，重点看三件事：MTEB 榜单只作参考，
领域评测集前若干结果的召回率才是关键，同时还要看向量化计算吞
吐。
后续优化可以从能力、成本和领域适配三条线展开：
评估 bge-m3 的多模态能力，用 Matryoshka
降维节省存储；有标注数据时，再考虑领域微调和指令微调。
向量存哪、怎么检索，这是向量库和索引的事。
向量库的候选包括 pgvector、Milvus、
Weaviate、Qdrant、Chroma 和 Elast
icsearch。
pgvector 的优势是复用 PostgreSQL 的事务
和联表能力；Milvus 面向分布式扩展；
Weaviate 内置混合检索；
已有 Elasticsearch 技术栈时，
也可以复用它的全文和向量能力。
常见索引算法包括 HNSW、IVF 和 Flat。
它们分别偏向低延迟、高规模或精确基线，具体选择要看压测，
不能只按数据量贴标签。
向量库怎么选，核心看三件事：规模、是否要事务和联表、
运维成本。
我的判断是：在中小规模、已有 PostgreSQL、
又需要事务和联表的场景里，可以先评估 pgvector。
理由很实在：后端团队熟悉 SQL，可以先按元数据过滤，
再按向量相似度排序，还能跟业务表联表、走事务，
少运维一个中间件。
规模、延迟或分片需求超过单库能力后，再评估 Milvus 等
分布式方案。
需要内置混合检索时，可以把 Weaviate 放进候选。
具体迁移阈值不能只看片段数量，要用压测决定。
以 pgvector 为例，一般同时建 HNSW 向量索引和
PostgreSQL 全文索引，为在线多路检索铺路。
一个库管理两种索引，不用再单独引入 Elasticsearc
h。
HNSW 参数可以先从常见组合开始压测。
构建阶段调整连接度和构建深度，查询阶段再调搜索深度，
通常要在召回和延迟之间取舍。
还要配合元数据打标，检索时先缩小候选集。
pgvector 的索引维护和空间回收也要进入运维计划。
在我参与的一个知识智能体项目里，我们选择 pgvector
的重要原因之一，就是它能和业务数据共享事务边界。
向量库和索引不能只看速度。
ANN 召回率要先和 Flat 暴力搜索对比，
再结合 QPS、延迟 P99 和内存占用设定业务门槛；
95% 可以作为一个评估起点，但不是所有场景的统一标准。
数据规模继续增长时，再逐步考虑 HNSW 参数调优、
用乘积量化或标量量化降低内存，以及多级索引、
分片和倒排文件索引配乘积量化这类超大规模组合。
上集先到这里。我们已经把原始文档经过解析、
分块、上下文增强和向量化，最终变成了可以检索的知识库。
